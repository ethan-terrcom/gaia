## Summary for the owner
The workflow can now really do the work. It creates or reuses the ticket's worktree and runs the
repo's setup command (with package-registry network only). It runs each plan step on the
configured agent: DeepSeek for the first two attempts, Claude for the third (`lead_attempt_from`,
your pending choice). It then runs the step's tests in the sandbox and commits each accepted step.
It also closes an old finding (F7: a failed worktree no longer blocks its branch forever).

The junior implemented my design faithfully. The one real problem was in **my** design: I had
told it to trust the plan's test command a little too much (X1). I fixed both halves of that.

## Findings

|---|---|---|---|---|
| X1 | **High** | `impl/steps.py` (the handoff's design), `orchestrator/lead.py` | A plan step's `test_command` (model output) went into `extra_allow`, and plan validation rejected only `deny`, not `ask`. A prompt-injected plan could make an approval-worthy command such as `bash -c …` run unasked. | **Fixed:** `extra_allow` = the owner's registered command only; plan test commands must be plainly *allowed* (an `ask` is sent back to the lead, then refused). **Checked and fine:**
- **Worktree setup:**
  - the "setup done" marker sits in `data_dir`, outside anything an agent can write;
  - F7: `failed` rows are revivable; an empty leftover dir is removed, a non-empty one is left for
    a human with a clear error;
  - the worktree is pinned via the trusted `git_dir`;
  - the setup command is not policy-checked (it is the owner's own, and runs before any agent),
    is network-limited to the registries, and its output is redacted;
  - `prepare_worktree` now runs outside the node's DB session.
- **Steps:**
  - runtimes are chosen from settings by `RuntimeKind` (P2), with no vendor names;
  - the lead takes attempt ≥ `lead_attempt_from`;
  - instructions wrap plan text and feedback with `wrap_untrusted`;
  - the per-step `base_sha` gives per-step diffs;
  - `diff_since` includes new files (intent-to-add).
- **Checks:** never ask; owner command only in `extra_allow`; no network; a scratch dir per check;
  output capped at 20K; the result persisted for the PR body.
- **Commits:** `[gaia] <title>`, Gaia author, idempotent on resume.
- **The integration test** runs the graph end to end with the real execution services, fake
  runtimes and a fake planner and reviewer, and reaches `completed`.

## Lesson
- **Leads make the permissive-default mistake too.** "Add the step's command to the allowlist"
  read as convenience and was a trust boundary. Every value a lead note routes into a policy input
  must be classified as owner-supplied or model-supplied. Added to the handoff skill.
