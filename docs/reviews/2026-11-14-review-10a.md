# Review: 10a — runtime base types, contract suite, fake runtimes

**Reviewer:** lead engineer (Claude) · **Implemented by:** DeepSeek junior (`deepseek-v4-pro`, sandboxed harness)
**Date:** 2026-11-14 · **Branch:** `impl/10a-runtime-base`

## Verdict
**Approve after lead fixes.** This is a solid, well-separated base for every runtime:
- `run_with_limits` owns the timeout, cancellation and `files_changed`;
- the environment is built from nothing;
- `stream_proc` reuses `run_proc`'s process-group and bounded-reap machinery;
- the orphan reaper fails closed;
- the contract suite runs against an in-process fake and a real-subprocess fake.

The review found **three bugs in the database approval broker**, one unbounded wait, and one
coverage hole that depended on the environment. All are fixed with tests.

## Findings

| ID | Severity | Where | Finding | Status |
|---|---|---|---|---|
| D1 | **High** | `DbApprovalBroker.request` | The waiter was registered **after** publishing `approval.requested`. A decision arriving during that `await` found no waiter, so the runtime sat out the whole timeout and returned **deny**, while the row said **approved**. | **Fixed:** the waiter is registered before publishing, and the final answer is read from the row. The regression test decides from inside the publish. |
| D2 | Medium | `DbApprovalBroker.decide` | It overwrote rows that were already decided or **expired**. A late click flipped `expired → approved` after the runtime had already been denied: a false audit trail. | **Fixed:** `ApprovalNotPending` (doc 14 → 409). |
| D3 | Medium | `DbApprovalBroker._upsert` | An identical repeated request reset a **rejected** row to pending, so a model could keep re-asking for a command the owner refused. | **Fixed:** approved or rejected rows are answered from the row; only expired ones are asked again. |
| S1 | Medium | `run_with_limits` | After a timeout or outer cancel it awaited `runtime.cancel()` **without a bound**, so a runtime with a hanging cancel defeated the timeout. | **Fixed:** `_cancel_bounded`, `CANCEL_GRACE_S = 10`. Test with a runtime whose cancel never returns. |
| C1 | Low | `tests/test_runtimes_orphans.py` | The `is_ours` → `ProcError` branch was covered only because `ps` could not start inside the junior's sandbox. Outside it, coverage dropped to 99%. | **Fixed:** a deterministic test. Added to the review skill's list. |
| L1 | Low | `gaia/config/logging.py` | Logs went to **stdout**, so CLI output (`dev run-task`, `dev plan`) wasn't valid JSON. The app lifespan reconfigures logging, so a per-command fix couldn't work. | **Fixed:** structlog defaults to a lazily resolved **stderr**. 11's `dev plan` special case is removed. |
| C2 | Low | `tests/test_runtime_contract.py` | The first **Linux CI** run failed: the orphan-reap test checked "pid gone" with a synchronous `kill(pid, 0)` loop, but a killed child stays a **zombie** until asyncio's watcher reaps it, which needs the event loop to run. macOS hid this. | **Fixed:** the helper is async (it yields to the loop) and counts a zombie as gone. |
| V1 | Info | `run_proc` / `stream_proc` | Suspected hang: a leader exits but a grandchild keeps the pipe open. **Disproved:** asyncio's `process.wait()` completes only when the pipes close, so the run stays bounded by `timeout_s`, and the group kill reaps the grandchild. | No change. |

Deferred, as the handoff planned: requirements 4 (budget), 10 (append-only history) and 11 (sandbox
launch) belong to the real runtimes, 10b and 10c.
