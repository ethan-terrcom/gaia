## Findings
| # | Severity | Where | Finding | Resolution |
|---|---|---|---|---|
| U1 | **High** | `hooks/useEventStream.ts` | The server sends **named** SSE events (`event: run.created`). Browsers deliver those only to `addEventListener(name)`, never to `onmessage`, and the hook used `onmessage` only. In a real browser the badge, spend and every live view would never update. The tests passed because the fake EventSource called `onmessage` directly. The handoff had flagged this exact question. | **Fixed:** one listener per name from `src/api/event-types.json`; a backend test keeps that file equal to `EventType`; the fake now delivers events like a browser; new tests. **Live:** Node's WHATWG `EventSource` against the server, with `onmessage` 0 of 7 events and named listeners 7 of 7. |
| U2 | Medium | same | The zod schema required `seq: number` and `id: string`, but the transport-only `stream.gap` marker has both `null`, so it was dropped. | **Fixed:** both are nullable, and `last_event_id` advances only on a real `seq`. Test added. |
| U3 | Low | `api/client.ts` | The badge fetched the whole inbox (up to 100 rows) to read one count. | **Fixed:** `status=pending&limit=1`. |

## Lessons for the skills
- **Fakes of browser APIs must follow the spec, not the code under test.** A fake EventSource that
  calls `onmessage` for every event, or a mock transport that decodes paths (15a), passes the
  junior's own model of the API. Review rule: compare each fake against the platform's documented
  behaviour, and prefer a real implementation (Node's `EventSource`, a bare git repo) for one
  live test.
- **Cross-language contracts need a test.** Values hard-coded on both sides (event names, the CSP)
  get one JSON source of truth and a backend test that compares.
- The harness's `npm run` support worked first time: 70 `run` calls, offline, with no npm
  cache errors.
