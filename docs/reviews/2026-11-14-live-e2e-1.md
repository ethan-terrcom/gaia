# Live end-to-end run 1: findings and fixes

- **Date:** 2026-11-14 · **Run by:** lead engineer (Claude)
- **What:** the first full run of Gaia driven through its HTTP API alone (`curl`), with real
  providers and the real sandbox. This is doc 14's acceptance criterion.
- **Verdict:** the pipeline works through to the commit. It found four bugs that no test had
  caught. All four are fixed in this PR, with tests.

## Summary for the owner
A ticket ("add `shout()` to `greet.py`, with tests") went through Gaia in a throwaway local repo:
- Claude planned the work;
- DeepSeek implemented it in the sandbox;
- the tests ran in the sandbox;
- Claude reviewed it;
- Gaia committed `[gaia] Add shout() to greet.py with tests`.

The run cost **$0.068**. It then stopped cleanly at "open PR", because the test repo has no GitHub
remote. The API token and the provider keys appear **zero** times in the logs.

The run exposed three bugs and a gap:
- a planning bug: the tests could not start in the sandbox;
- a lifecycle bug: cancelling a run left a stale approval in your inbox, and deciding it crashed
  the graph;
- a gap: the "open PR?" approval did not show you what you were approving.

**One decision for you (recommendation below):** what a run should do when the repository has no
GitHub remote.

## Setup
- A local server on port 8799, started from this branch with an empty data dir. Keys were held in
  memory only; the Keychain was not touched.
- A throwaway git repo with a uv project (`greet.py`, one test). It was registered through
  `POST /repositories`, with a ticket created through `POST /tickets`.
- The roles were the defaults:
  - the lead (plan, review) was Claude through `claude_agent_sdk`;
  - the junior was DeepSeek through `NativeRuntime`;
  - the setup and test commands ran under `srt`.
- The run was driven only with `POST /runs`, `GET /runs/{id}`, `GET /approvals` and
  `POST /approvals/{id}/decide`.

## Findings

| # | Severity | Finding | Fix |
|---|---|---|---|
| L1 | High | The lead's plan used a bare `pytest` as each step's `test_command`. Inside the sandbox there is no project venv on `PATH`, so the command exited with 127 and every step "failed its tests". The plan validator only checked the allowlist. | `plan_ticket` now tells the lead the repository's registered test command. Plan validation rejects a step whose `test_command` does not **start with** that command. |
| L2 | High | **Cancelling a run left its pending approvals pending.** Deciding one afterwards resumed a cancelled graph. The guard returned `{}` for a terminal run, so the old `route` (`escalation`) stayed in state, and the conditional edge raised `KeyError: 'escalation'`. | (A) `cancel` and a failed run both expire the run's pending approvals (`status=expired`, with a comment) and publish `approval.decided {action: "expired"}`, so the inbox clears live. (B) `POST /approvals/{id}/decide` returns **409 `run_not_active`** for a run that has finished. (C) The guard returns `{"route": "end"}` for a terminal run. **The same latent bug** was in the budget-reject path, which cancels the run and returned `{}`; it is fixed the same way. |
| L3 | Medium | The `pr_open` approval's payload was `{"kind": "pr_open"}`, so the human approved a PR without seeing the lead's review (doc 14, task 3). | (D) The payload now includes `review` (verdict, summary, findings). The e2e API test asserts it. |
| L4 | Low (tooling) | While adding tests for L2, coverage reported lines it had run as missed, and lines it had not run as covered. SQLAlchemy's async engine switches greenlets on every `await`, and the tracer was not told. | `[tool.coverage.run] concurrency = ["greenlet", "thread"]`. This makes measurement **more** accurate and relaxes nothing; the suite still needs 100%. It costs about 25 s per full run. |

## Verified
- Plan → approve → implement → setup (`uv sync` in srt) → tests in srt → review → commit, all
  through the API.
- Cancel with a pending approval left an approval that resumed a dead graph (before the fixes).
  After the fixes, the test suite covers each path:
  - cancel expires the approval and publishes the event;
  - a failure does the same;
  - deciding for a finished run returns 409;
  - a terminal run routes to `end`.
- Redaction: the token and both keys were grepped for in the console log and `gaia.jsonl`: 0 hits.
- `make check` items: ruff, format, mypy strict, pytest at 100% (1817 passed).

## Decision for the owner: repositories without a GitHub remote
Today a run on a repo with no GitHub remote ends as **`failed`** at `open_pr`, even though the work
is done and committed on the run's branch.

**Recommendation:** end such a run as **`completed`**, with a `run.note` event saying "no GitHub
remote; branch `gaia/…` left for you to merge". Skip the PR and merge gates. A local-only repo is
a legitimate use of a local-first tool, and "failed" would teach users to ignore failures. The
alternative is to refuse to start a run on such a repo (a 409 at `POST /runs`). That is simpler,
but it blocks a real use case. I have not built either; this needs your call.

## Not done here
- The run did not reach `open_pr`, `watch_ci` or `merge` against GitHub. Those need a sandbox
  GitHub repo and a fine-grained token, which is a separate owner question. Their logic is covered
  by 15a/15b's tests against a fake GitHub, whose request shapes were checked against GitHub's
  docs in review.
