# Code review: implementation packages 01–05

**Reviewer:** lead engineer · **Date:** 2026-11-13 · **Scope:** everything merged to `main`
through PR #9 (docs 01 scaffolding, 02 config & secrets, 03 database, 04 API & auth, 05 git &
worktrees) · **Branch:** `review/01-05-senior-review`

## Verdict

The work is in good shape. All five packages meet their acceptance criteria:
`make check` is green, with 342 backend tests at 100% line and branch coverage, strict mypy, and
gitleaks clean over the full history. Each doc records its deviations honestly and with reasons.
The security conventions are enforced by tooling, not just by review. Highlights:

- Only `gaia/services/proc.py` may spawn a process, and ruff (`TID251`) fails the build anywhere else.
- Child processes get an **allowlisted** environment, so no provider key can leak into one by default.
- Repo hooks, signing and pagers are neutralised on every git call.
- The bearer token is compared in constant time on bytes, and error envelopes are redacted.
- Every tenant query goes through `ScopedRepo`. Routes only ever receive a `Scoped` object, so a
  route cannot forget the workspace filter.

I fixed one small bug (below). There is **one blocking security finding (F1)** that must be fixed
before any agent writes into a worktree (docs 09a/10b), and five design decisions to settle before
docs 06 and 12a. Each finding below has a recommendation.

### F1 — Critical (blocks 09a/10b/12b): planted git config runs code in Gaia's unsandboxed git

**What.** A worktree's `.git` is a *file* (`gitdir: <path>`) that sits inside the worktree, so an
agent can overwrite it. If it points at a git directory the agent wrote, Gaia's next git call in
that worktree (`is_dirty`, `commit`, `diff`, …) reads the attacker's config. Git config can name
commands to execute (`core.fsmonitor`, `filter.<x>.clean`, `diff.external`, textconv drivers, and
others). Gaia's own git runs **outside** the D1 sandbox, with access to the keychain and `~/.ssh`.
So this is a sandbox escape: an allowlisted `pytest` writes the payload from a `conftest.py`, and
Gaia executes it.

**Evidence.** I reproduced it against the merged code (scripts are in this session's scratchpad,
not committed). With only worktree-local writes, `GitService.is_dirty()` executed a planted
`core.fsmonitor` command, and `git add` executed a planted clean filter. Adding
`-c core.fsmonitor=false` blocks the first but not the second: `-c` overrides can never cover every
exec-capable key.

**Exposure today:** none. No agent writes to worktrees until 09b/10b. It must be closed before then.

**Recommendation (a small PR, "05b git hardening", before 09a):**
1. Every git call whose `cwd` is a worktree runs with `GIT_DIR=<repo>/.git/worktrees/<name>` and
   `GIT_WORK_TREE=<worktree path>`, both resolved from the **trusted repository side** and never from
   the worktree's `.git` file. I verified this blocks both vectors above. Record the admin directory
   on the `worktree` row at creation (a new `git_dir` column, migration `0002`). Re-derive it by
   scanning `<repo>/.git/worktrees/*/gitdir` when reconciling.
2. Expose this as `GitService` methods that take a `Worktree` rather than a bare path, so a caller
   cannot forget the pin.
3. Defence in depth: add `-c core.fsmonitor=false` to `HARDENED_CONFIG`, and pass
   `--no-ext-diff --no-textconv` to `diff`.
4. If a worktree's `.git` file no longer matches the recorded admin directory, refuse the call, write an
   audit row and raise a `worktree.tampered` event.
5. Turn the reproduction into regression tests, and add "planted `.git` file / git config" to the
   18d checklist.

### F2 — Medium (before 09b `run_command`): a process that leaves its group escapes the timeout

**What.** `run_proc` kills the child's process group on timeout. A grandchild that calls `setsid()`
is no longer in that group. It keeps stdout open, so `await process.wait()` (which also waits for
the pipes) blocks until the escapee exits. It then keeps running after `run_proc` returns.
Reproduced: `timeout_s=1.0` returned after 8 s, and with a longer sleep it does not return at all.

**Exposure today:** none, because only git uses `run_proc`. Agent commands in 09b will.

**Recommendation:** bound the reap after a kill: wait a short grace period, then close the pipe
transports, cancel the readers and return with a new `escaped=True` flag. Run agent commands under
the D1 sandbox in a per-run session so stragglers can be found and killed. 18c's Docker runner kills
the whole container, which is the complete answer. Assign this to 09a (the sandbox profile) or fold
it into 05b.

### F3 — Medium (decide in 12a): two run transitions the graph will need are illegal

- `failed → <anything>` is refused. `domain/state.py` says "doc 12 resumes a failed run from its
  checkpoint", but the resumed node cannot move the row off `failed`. The run would continue in the
  graph while its row stays `failed`, or the guard would raise `IllegalTransition` again.
- `pending → paused_budget` is refused. 12's `with_guard` checks the budget before *every* node,
  including the first one, so a run started after the daily cap would crash instead of pausing.
- Related: doc 12 moves the ticket to `in_progress` on the first step, but `backlog → in_progress` is
  illegal (only `ready` may start).

**Recommendation:** add `pending → paused_budget`. Allow
`failed → planning | implementing | reviewing | awaiting_approval` **only** through an explicit
`RunManager.retry(run_id)` that the owner triggers, and audit it. Have `POST /runs` (14) require a
`ready` ticket, or move `backlog → ready` itself. These are small edits to one dict plus tests; the
decision belongs to 12a.

### F4 — Medium (12a): approvals have no idempotency key

ARCHITECTURE §4 and doc 12 require the `approval` row to be **upserted**, keyed by
`(run_id, node, step_index, attempt)`, because a node re-runs from its first line on resume. The
table has none of those columns and no unique constraint, so a resumed `approve_plan` would insert a
duplicate request into the inbox.

**Recommendation:** migration `0002` (shared with F1) adds `node`, `step_index`, `attempt` and
`UNIQUE(run_id, node, step_index, attempt)` to `approval`.

### F5 — Medium (06, then before multi-user): nothing stops cross-workspace references

`ScopedRepo` filters *reads* by workspace, but a *write* can still point a child row at a parent in
another workspace. For example, a `ticket` in workspace B can reference a `repository` in workspace A.
`tests/test_worktree_service.py::test_open_in_editor_refuses_a_row_from_another_workspace` builds
exactly such a row. This does not matter while there is one workspace. It is the main multi-tenant
hole for later.

**Recommendation:**
- **Now:** add to doc 06's tasks that every route loads parent rows through `ScopedRepo.get` before
  it writes a child, which returns 404 otherwise.
- **Before multi-user:** composite foreign keys, `(workspace_id, repo_id) → repository(workspace_id, id)`
  and so on, so the database enforces the boundary.

### F6 — Medium (before 06): `get_session` commits after the response has been sent

Documented as doc 04 deviation 9. A `POST` whose commit fails (a unique-constraint violation, a
locked database) has already answered `201`. The rule "commit inside the handler when it matters"
relies on every future route author remembering it, and the first mutating routes arrive in doc 06.

**Recommendation:** before 06, change the default so that it is safe. The installed FastAPI
(0.162.5) supports `Depends(get_session, scope="function")`, which runs the dependency's teardown,
and so the commit, **before** the response is sent. Switching `SessionDep` to it is a one-line change. Add a
test where a commit fails and the client receives a 409/500 rather than a 2xx.

### F7 — Low: a failed worktree creation wedges the ticket's branch

`create()` revives only `removed` rows. A `failed` row (from a timeout, say) raises
`WorktreeAlreadyExists` forever. And if the caller's transaction rolls back on the error, which it
does under `session_scope`, the `failed` marker is lost while a half-created directory may remain.
**Recommendation:** treat `failed` like `removed`: prune, delete any leftover directory under the
root, then retry. Run `create()` in its own committed transaction (decide in 12b).

### F8 — Low (18b/13): logs from outside structlog are not redacted

uvicorn's access log and SQLAlchemy log through the standard `logging` module, which bypasses the
structlog redaction processor. Once doc 13 lands, the access log will record `?ticket=` query strings.
Those tickets are single-use and expire in 60 s, so the risk is low. **Recommendation:** in 18b, route
stdlib logging through `structlog.stdlib.ProcessorFormatter` so one redaction chain covers everything.

### F9 — Low (cloud path): `event.seq` ordering under Postgres

On SQLite there is a single writer, so `seq` order is commit order. On Postgres, a sequence value is
taken before commit, so two concurrent writers can commit out of order. SSE replay (`seq > last`)
could then skip an event. **Recommendation:** note it in doc 13. Keep a single writer per process (the
`EventBus`) and revisit before the Postgres move.

### F10 — Low: the coverage bar is not enforced

Coverage is 100% but nothing fails if it drops. **Recommendation:** add `fail_under = 100` (or 95, if
you'd rather leave room) under `[tool.coverage.report]`. This is your call as a policy, so I did not
change it.

### Observed, no action

- `LocalTokenAuth` reads the keychain on every request. It runs in FastAPI's threadpool, so it does not
  block the event loop, and it lets a token regenerated by `gaia ui` take effect without a restart.
  Fine for v1; revisit with OIDC.
- Keychain items can be read by any process running the same Python binary (the macOS ACL trusts the
  creating application). This is already on the 18d checklist, and D1's sandbox is the control.
